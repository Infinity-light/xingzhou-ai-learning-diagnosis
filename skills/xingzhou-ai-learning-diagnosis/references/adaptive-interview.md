# 自适应访谈

## 最小回答负担

“问题少”不能靠把四五个问题塞进一句话实现。每轮只让用户完成一个回答动作，并允许他用一个词、一个序号、一句话或一个路径作答。信息足够就停止，通常一到两个短问题，绝不超过三个。

每个追问应同时满足三点：答案会改变相邻分数节点的判断；用户能从一件已经发生的事情或现存产物回答；答案会改变下一步路线。否则不问。

禁止让用户假设未来再次发生时会怎样，也不要让用户替系统解释可重复性、检查点、恢复机制或证明链。Agent 应从实际经历和产物中推断这些能力；缺少真实事件就标为尚未展示。

E0–E3、内部证据卡和临时分数只供 Agent 判断。最终诊断前不要展示它们，也不要用量表术语向用户解释为什么要问。

## 先锁定一件事情

按下面的顺序选择入口：

1. 当前对话已经围绕一件具体任务展开：直接使用它，不要求用户重新讲一遍。
2. 对话中有多个候选任务：只列最近或信息最完整的最多三个名称，让用户回复一个名称或序号。不要先总结他的全部 AI 履历。
3. 没有任何具体任务：只问事情名称。

没有候选任务时可以问：

> 我们先只看一件事：最近一次你确实让 AI 帮你做了什么？只说事情名称就行，比如“改一篇文案”“做一张图”或“处理一个项目”。

只知道事情名称而不知道结果时，可以用一个低负担选项题：

> 这件事最后最接近哪一种：①没实际用上；②这一回实际用了；③后来又用同样办法做成过；④已经有固定流程跑过多次？回一个序号就行。

选项只是帮助回忆，不能直接换算分数。用户若给出更具体的事实，以事实为准。已有上下文能回答这道题时直接跳过。

用户正在验收一个 AI 产物时，安装、实际运行、指出具体缺陷、要求修改都属于已经发生的事实，应直接纳入判断。若用户已经说清“哪里没通过”，不要再问他凭什么判断；只在确实影响下一分数节点时，追问一项此前真实发生的复用、故障、恢复或产物记录。

## 按真实证据选择一个追问

下面是问题库，不是问卷。每轮只能选择其中一个问题，并改写成用户刚才使用的语言。

| 待区分的分数 | 只在对应事实尚缺时选一个问题 | 主要区分 |
| --- | --- | --- |
| 0↔1 分 | “你实际用 AI 做过哪一件小事？只说事情名；确实没有就答‘没有’。” | 听说过 AI 与真实尝试 |
| 1↔3 分 | “那次第一版出来后，你接着做了什么？” | 单次问答与主动调整 |
| 3↔5 分 | “那次最后真正被你采用的是哪一部分？没采用就答‘没采用’。” | 迭代与现实采用 |
| 5↔7↔10 分 | “你最后看了哪一处，才决定这个结果可以用了？” | 采用结果与可靠闭环 |
| 10↔15 分 | “除了这次，你后来还用同样办法完成过哪一件事？只说任务名；没有就答‘没有’。” | 单次完成与真实复用 |
| 15↔20 分：失败可见性 | “回想最近一次没顺利完成，你最先从什么迹象发现它卡住了？” | 失败是否真实可见 |
| 15↔20 分：恢复 | “那次出错后，你是从头重做，还是保留已有结果接着继续？” | 是否有可恢复状态 |
| 15↔20 分：完成证据 | “最近一次完成后，留下了哪个文件、页面或记录可以回看？” | 完成是否有可核对痕迹 |
| 20↔30 分 | “除了刚才这次，最近一次按同样流程完成的是什么？没有就答‘没有’。” | 可恢复结构与多次稳定运行 |
| 30↔40 分 | “这套方法实际换到另一个项目或给另一个人用过吗？说一个名字和结果；没有就答‘没有’。” | 单项目成熟与真实迁移 |
| 40↔50 分 | “最近哪次失败让你改掉了一条原有规则？只讲改掉的那一条。” | 经验积累与基于反例的取舍 |
| 50↔60 分 | “最近一次别人按这套方法做出了什么可以检查的结果？有链接或文件可直接给。” | 个人方法与持续外部采用 |
| 60↔75 分 | “哪一个真实反例迫使你修改过自己的核心判断？” | 方法体系与可反驳原创框架 |
| 75↔90 分 | “哪一项独立结果最能说明这套方法离开你仍然有效？” | 自述影响与独立长期影响 |
| 90↔100 分 | 优先检查长期独立证据，不用一道自述题授予 100 分。 | 领域影响与北极星 |

15↔20 分有三种问题，只能根据当前最关键的未知选择一个，不能连续抛给用户。用户没有经历过真实失败时，不得要求他编造；保留未知，必要时改查现有产物。

## 第三问门槛

只有一个尚缺事实会改变分数区间或学习路线时才问第三题。优先补：实际结果、验收动作、真实复用、一次真实迁移，或高阶段主张的可核对产物。

第三题仍然只补一个事实。例如：“你说已经给三个人用过，能给我其中一次产物或验收记录吗？”用户不知道、忘了、不想答或没有记录时立即停止，不换一种说法继续盘问。

## 进阶项目检查

用户提供路径后，先声明只读检查对象和范围，然后自己完成，不把文件列表交给用户整理。优先寻找：

- README、目标或需求说明；
- 实际输入、工具调用或数据来源；
- 测试、评测、验收回执和失败样本；
- 状态、恢复、回滚、权限和人工接管设计；
- 多次运行、版本演化、真实用户反馈或跨项目复用痕迹。

将发现写成“文件或记录 → 可支持的行为主张 → 不能证明的部分”。不要读取凭据和与诊断无关的私人内容。复杂项目也可能只有较低分数证据，简单项目也可能形成完整闭环。

## 新手友好

用户没有项目、不会安装工具或只用过聊天产品，都不构成失败。如果用户想不起案例，给出“文案、图片、资料、表格、代码、生活问题”中最多三个贴近上下文的选项；仍然没有经历就停止访谈，给一个今天可完成的小基准任务。

如果平台不能读本地文件，使用对话证据完成诊断并降低置信度。不要要求用户为了评分先搭技术环境。
